# PRD-007：模拟支付与幂等回调

## 1. 阶段信息

- 状态：预规划
- 前置条件：PRD-006 验收通过
- 核心技术：支付适配器、HMAC、MySQL 事务、幂等消费
- 阶段目标：完成订单支付闭环，并正确处理外部回调可能延迟、重复、乱序或伪造的问题。

## 2. 功能范围

- 为待支付订单创建模拟支付单。
- 返回模拟支付页面/动作需要的信息。
- 模拟成功、失败和取消结果。
- 接收带签名的异步支付回调。
- 校验支付单、订单、用户、币种和金额。
- 支付成功后将订单推进至 `paid`/`pending_shipment`。
- 保存支付流水、渠道交易号和回调摘要。
- 支持消费者查询支付状态。
- 重复创建支付和重复回调不会产生重复业务效果。

## 3. 数据变化

新增：

- `payments`：支付单号、订单、用户、金额、币种、渠道、状态、过期时间和时间戳。
- `payment_callbacks`：渠道事件 ID、签名校验结果、载荷摘要、处理状态和错误。

关键唯一约束：

- 一个订单同一时间最多有一个有效待支付支付单。
- 渠道交易号唯一。
- 渠道事件 ID 唯一，用于回调幂等。

支付状态至少包含：

```text
pending -> succeeded
pending -> failed
pending -> cancelled
```

成功状态不可退回 pending，退款由 PRD-009 单独建模。

## 4. 技术设计

定义支付适配器接口，业务层不直接依赖模拟渠道 HTTP 细节：

- 创建支付。
- 验证回调签名。
- 解析渠道事件。
- 查询支付状态。
- 发起退款能力留到 PRD-009 扩展。

模拟回调使用 HMAC 签名。密钥通过环境配置注入，不写入仓库。保存回调时只保留完成排查所需的数据，避免无边界保存敏感原始内容。

## 5. API 增量

消费者：

```text
POST /api/v1/orders/:id/payments
GET  /api/v1/orders/:id/payment
```

模拟支付渠道：

```text
POST /api/v1/mock-payments/:payment_no/result
POST /api/v1/payment-callbacks/mock
```

模拟结果接口仅用于开发和测试环境，生产模式必须禁用。

## 6. 核心规则

- 只有订单所有者可以创建和查询支付单。
- 只有待支付订单可以创建支付单。
- 支付金额和币种完全由订单生成，不接收前端指定值。
- 回调必须先验签，再解析和处理业务。
- 回调金额、订单号、支付单号不一致时拒绝推进订单。
- 支付成功、订单状态变化、库存从预占转确认及状态日志在同一事务中完成。
- 重复回调返回成功确认，但不能重复确认库存或写多次状态变化。
- 对未知支付结果不得自行假定成功或失败。

## 7. 实施步骤

1. 定义支付与订单状态扩展及不变量。
2. 创建支付单、回调记录迁移和唯一约束。
3. 定义支付 Provider 接口和模拟实现。
4. 实现创建支付单与支付状态查询。
5. 实现 HMAC 签名、校验和防重放基础规则。
6. 实现回调落库、幂等判断和事务处理。
7. 推进订单状态并确认库存预占。
8. 实现开发环境模拟结果接口。
9. 增加重复、乱序、篡改和并发回调测试。

## 8. 测试要求

- 非订单所有者不能创建或查看支付单。
- 前端无法篡改支付金额。
- 错误签名、错误金额和未知支付单回调被拒绝。
- 同一渠道事件并发到达只有一次业务效果。
- 支付成功后订单、支付、库存和状态日志保持一致。
- 已取消订单晚到的成功回调进入明确异常处理路径，不能静默改成已支付。
- 模拟支付接口在生产配置下不可访问。

## 9. 验收标准

- 待支付订单能完成模拟支付并进入待发货状态。
- 回调签名与金额校验有效。
- 重复、并发和乱序回调不会破坏订单状态。
- 支付处理失败时不存在半提交状态。
- 可以通过支付单号和订单号追踪处理记录。
- 自动化测试与竞态检查通过。

## 10. 本阶段不做

- 不对接真实微信、支付宝或银行卡渠道。
- 不处理真实资金和敏感卡数据。
- 不实现退款、分账或多币种。

## 11. 阶段出口

交易主流程已能从待支付进入待发货，并具备外部事件幂等处理能力。下一阶段把超时关单和通知等副作用移到可靠后台任务。
