# PRD-012：可观测性、压测与最终验收

## 1. 阶段信息

- 状态：预规划
- 前置条件：PRD-011 验收通过
- 核心技术：`log/slog`、Prometheus、Grafana、k6、pprof、MySQL EXPLAIN
- 阶段目标：让问题可定位、性能可量化、容量假设可复现，并完成商城总 PRD 的最终验收。

## 2. 可观测范围

### 日志

- 全部 HTTP 请求具有请求 ID；尊重可信 Nginx 传入值，否则服务端生成。
- 使用 `log/slog` 输出结构化 JSON。
- 记录路由模板、状态码、耗时、用户 ID 摘要和错误分类。
- 订单、支付、退款和任务日志携带对应业务标识。
- 禁止记录密码、token、Cookie、支付签名和完整敏感资料。

### 技术指标

- HTTP 请求数、进行中请求、错误率和延迟直方图。
- MySQL 连接池使用、等待、查询错误和慢查询计数。
- Redis 命中、未命中、超时、错误和降级次数。
- worker 任务积压、执行耗时、重试和失败数量。
- Go 运行时 goroutine、GC 和内存指标。

### 业务指标

- 商品浏览和搜索次数。
- 订单创建成功、库存不足、取消和支付成功数量。
- 支付回调重复、验签失败和处理失败数量。
- 优惠券领取、退款申请/成功和低库存 SKU 数量。

## 3. 组件与访问控制

- API 暴露 Prometheus 指标端点，仅允许内部网络访问。
- Compose 增加 Prometheus 和 Grafana。
- Grafana 提供 API、数据库缓存、交易和任务四类看板。
- pprof 默认关闭或仅内部鉴权访问，禁止公开暴露。
- 指标 label 禁止使用订单号、用户 ID、URL 原始值等高基数字段。

## 4. 压测场景

统一使用 k6，脚本和测试数据生成方式提交到仓库。

参考环境：

- Docker 可使用至少 4 CPU、8 GB 内存。
- 两个 API 实例。
- 10,000 个商品、50,000 个 SKU、5,000 个测试用户。
- 测试前预热缓存，另设冷缓存对照场景。

初始性能目标：

| 场景 | 负载 | 目标 |
| --- | --- | --- |
| 商品列表/详情混合读取 | 200 RPS，持续 5 分钟 | P95 < 200 ms，系统错误率 < 1% |
| 登录 | 20 RPS，持续 2 分钟 | P95 < 500 ms，无非预期限流绕过 |
| 创建订单 | 30 RPS，持续 3 分钟 | P95 < 800 ms，无超卖、无重复订单 |
| 热点有限库存并发购买 | 500 并发请求 | 成功数不超过库存，库存不为负 |

业务预期的 `409 库存不足` 不计作系统错误，但必须单独统计。若本机环境无法达到参考资源，报告必须记录实际资源并给出基线，不得删除正确性校验换取数字。

## 5. 故障演练

- 停止一个 API 实例，验证 Nginx 继续服务。
- Redis 短时不可用，验证缓存降级与高风险限流策略。
- MySQL 短时不可用，验证请求超时、就绪状态和恢复。
- worker 执行过程中重启，验证任务恢复和幂等性。
- MinIO 不可用，验证商品核心数据仍可查询且图片错误可解释。
- 注入慢查询，验证超时、连接池指标和日志定位能力。

每个演练记录预期行为、实际结果、恢复时间和遗留风险。

## 6. 性能分析与优化规则

- 先建立基线并通过日志、指标、pprof 或 EXPLAIN 找到证据。
- SQL 优化先检查查询模式和索引，不盲目增加缓存。
- CPU/内存问题使用 pprof 定位，不凭感觉重写。
- 优化前后使用同一脚本、数据量和资源条件比较。
- 任何优化不能破坏事务、幂等、权限和库存正确性。
- 所有超时、连接池和并发参数提供默认值与配置说明。

## 7. 文档交付

- 项目架构与模块边界。
- 本地开发依赖和启动方式。
- 环境变量及安全说明。
- 数据库迁移、初始化和备份恢复演示。
- 自动化测试和压测命令。
- OpenAPI 接口文档。
- Nginx、Docker Compose 和故障排查手册。
- 关键技术决策记录：MySQL、Redis 缓存、订单事务、Outbox、限流和对象存储。

## 8. 实施步骤

1. 统一请求 ID 和 slog 字段规范。
2. 为 HTTP、MySQL、Redis 和 worker 添加指标。
3. 添加订单、库存、支付和退款业务指标。
4. 配置 Prometheus 抓取和 Grafana 看板。
5. 编写可重复的测试数据生成工具。
6. 编写 k6 浏览、登录、下单和热点库存脚本。
7. 建立冷/热缓存与正常负载性能基线。
8. 使用 EXPLAIN、pprof 和指标定位主要瓶颈并做有证据的优化。
9. 执行依赖与实例故障演练。
10. 完善全部运行、接口、部署和排障文档。
11. 按总 PRD 执行端到端最终验收。

## 9. 测试与验收

- 自动化测试、竞态测试和静态检查全部通过。
- 指标端点不公开泄露业务数据或敏感标识。
- 可以从一个请求 ID 定位失败订单的关键处理记录。
- Grafana 可以观察请求、依赖、交易和任务状态。
- 压测结果包含环境、数据、脚本、指标、瓶颈和结论。
- 故障演练结果符合各阶段定义的降级与恢复策略。
- 并发下单在压测下仍无超卖、重复订单和金额错误。
- 总 PRD 第 10 节完整业务流程全部演示通过。

## 10. 本阶段不做

- 不为追求微服务、Kubernetes 或服务网格而重构系统。
- 不搭建生产级 24x7 告警值班体系。
- 不承诺脱离参考环境的绝对性能数字。

## 11. 最终完成定义

GoMall 在功能正确、数据一致、安全边界、自动化测试、多实例部署、可观测性和性能报告全部验收后完成。后续新增功能必须重新进入产品需求、设计、实现、测试和验收流程。
