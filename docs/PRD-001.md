## 2. 阶段目标

实现一个可运行、可测试、并发安全的商品目录 API。运营人员可以管理商品和 SKU，消费者只能看到允许销售的商品。

本阶段重点验证以下能力：

1. 使用 Go 对商品和 SKU 建模。
2. 使用 Gin 设计清晰的管理端和消费者端 API。
3. 使用 controller、service、repository 分离 HTTP、业务与存储职责。
4. 使用明确的错误值表达业务失败。
5. 使用 GORM 将商品和 SKU 持久化到 Docker MySQL。
6. 使用 `config.yaml` 管理服务和数据库配置。
7. 使用自动化测试固定业务规则和数据库约束。

## 4. 业务术语

### 4.1 商品

商品是消费者看到的一个商品页面，例如“GoMall Logo T 恤”。商品保存所有规格共同使用的名称、描述和销售状态，但不直接保存成交价格和可售库存。

商品可以理解为父级信息，数据库中对应 `products` 表的一行。

### 4.2 SKU

SKU 是 Stock Keeping Unit 的缩写，可以理解为“消费者最终选中的具体规格”。

例如商品“GoMall Logo T 恤”有不同颜色和尺码：

| SKU Code         | 规格       |    价格 | 库存 |
|------------------|------------|--------:|-----:|
| `TSHIRT-BLACK-M` | 黑色、M 码 | 5900 分 |   12 |
| `TSHIRT-BLACK-L` | 黑色、L 码 | 5900 分 |    4 |
| `TSHIRT-WHITE-M` | 白色、M 码 | 6900 分 |    0 |

它们共用同一个商品名称和描述，但每个 SKU 独立保存规格、价格、库存和状态。消费者加入购物车、创建订单和扣减库存时，操作的是确定的 SKU，而不是只有商品。

一个商品和 SKU 的关系：

```text
商品：GoMall Logo T 恤
├── SKU：黑色 / M 码
├── SKU：黑色 / L 码
└── SKU：白色 / M 码
```

数据库中 `skus.product_id` 指向所属商品的 `products.id`，形成一对多关系。即使商品只有一种形式，也需要创建一个默认 SKU 来保存价格和库存。

完整术语解释和操作流程见[初学者术语表](./GLOSSARY.md)。

### 4.3 金额

所有金额使用人民币最小单位“分”的整数表示：

- `1999` 表示 `19.99` 元。
- 禁止使用 `float32` 或 `float64` 保存和计算金额。
- 接口字段明确命名为 `price_cent`，避免单位歧义。

## 5. 数据模型

### 5.1 Product

| 字段        | Go 建议类型      | JSON 字段     | 规则                           |
|-------------|------------------|---------------|--------------------------------|
| ID          | `uint64`         | `id`          | 系统生成，大于 0，不可修改     |
| Name        | `string`         | `name`        | 去除首尾空白后 2～100 个字符   |
| Description | `string`         | `description` | 可为空，最多 2000 个字符       |
| Status      | 自定义字符串类型 | `status`      | `draft`、`on_sale`、`off_sale` |
| CreatedAt   | `time.Time`      | `created_at`  | 系统生成，RFC 3339 输出        |
| UpdatedAt   | `time.Time`      | `updated_at`  | 每次成功变更时更新             |

商品详情响应还应包含 `skus` 数组；商品列表是否返回完整 SKU 由接口契约明确规定。

### 5.2 SKU

| 字段      | Go 建议类型         | JSON 字段    | 规则                       |
|-----------|---------------------|--------------|----------------------------|
| ID        | `uint64`            | `id`         | 系统生成，大于 0，不可修改 |
| ProductID | `uint64`            | `product_id` | 必须关联存在的商品         |
| Code      | `string`            | `code`       | 全局唯一，3～32 位         |
| Specs     | `map[string]string` | `specs`      | 至少 1 项，最多 5 项规格   |
| PriceCent | `int64`             | `price_cent` | 大于 0                     |
| Stock     | `int64`             | `stock`      | 大于等于 0                 |
| Status    | 自定义字符串类型    | `status`     | `active`、`inactive`       |
| CreatedAt | `time.Time`         | `created_at` | 系统生成，RFC 3339 输出    |
| UpdatedAt | `time.Time`         | `updated_at` | 每次成功变更时更新         |

SKU 编码规则：

- 去除首尾空白后校验。
- 只能包含大写字母、数字、下划线和连字符。
- 必须以大写字母或数字开头。
- 区分输入错误，不由服务端自动转换大小写。
- 示例：`TSHIRT-BLACK-M`、`BOOK_GO_001`。

规格规则：

- key 和 value 去除首尾空白后都不能为空。
- key 最多 20 个字符，value 最多 50 个字符。
- 示例：`{"颜色":"黑色","尺码":"M"}`。

## 6. 状态规则

### 6.1 商品状态

```text
draft ──────> on_sale ──────> off_sale
                 ▲               │
                 └───────────────┘
```

允许的状态迁移：

| 当前状态             | 目标状态   | 是否允许 | 条件                      |
|----------------------|------------|----------|---------------------------|
| `draft`              | `on_sale`  | 是       | 至少存在一个 `active` SKU |
| `on_sale`            | `off_sale` | 是       | 无额外条件                |
| `off_sale`           | `on_sale`  | 是       | 至少存在一个 `active` SKU |
| 任意状态             | 相同状态   | 否       | 返回状态未变化错误        |
| `on_sale`/`off_sale` | `draft`    | 否       | 草稿状态不可恢复          |

商品创建后固定为 `draft`，客户端不能在创建请求中指定其他状态。

### 6.2 SKU 状态

- SKU 创建时默认状态为 `active`。
- `active` 与 `inactive` 可以相互切换。
- SKU 状态与库存是两个概念：库存为 0 的 SKU 仍可处于 `active`，但消费者端展示为售罄。
- 上架商品必须至少保留一个 `active` SKU。
- 若某操作会使上架商品失去最后一个 `active` SKU，则拒绝该操作。

### 6.3 删除规则

- `on_sale` 商品不能删除，必须先下架。
- 删除商品时同时删除其全部 SKU。
- 删除商品和 SKU 使用 GORM 软删除，数据库保留历史记录。
- 上架商品的 SKU 不能删除。
- 删除不存在的商品或 SKU 返回 `404`。

## 7. API 通用约定

### 7.1 基础路径

- 运营接口：`/api/v1/admin`
- 消费者接口：`/api/v1`
- 健康检查：`/health/live`

### 7.2 Content-Type

- 有 JSON 响应体的接口返回 `application/json; charset=utf-8`。
- JSON 请求必须使用 `Content-Type: application/json`。

### 7.3 成功响应

单个资源：

```json
{
	"code": 200,
  "data": {
    "id": 1,
    "name": "Go 语言实战课程"
  }
}
```

列表资源：

```json
{
	"code": 200,
  "data": [],
  "meta": {
    "page": 1,
    "page_size": 20,
    "total": 0
  }
}
```

空列表必须返回 `[]`，不能返回 `null`。

### 7.4 错误响应

所有业务错误采用统一格式：

```json
{
	"code": 404,
	"message": "商品不存在"
}
```

`code` 与 HTTP 响应状态码保持一致。错误响应不能暴露 Go 类型、调用栈或内部实现细节。

### 7.5 分页规则

- `page` 默认值为 1，必须大于等于 1。
- `page_size` 默认值为 20，范围为 1～100。
- 超出范围返回 `400`，不静默修正。
- 默认按 `created_at` 从新到旧排序；时间相同时按 `id` 从大到小排序。

### 7.6 JSON 参数绑定

Controller 使用 Gin 的 `ShouldBindJSON` 将 JSON 请求参数绑定到 Request 结构体。JSON 语法错误或字段类型不匹配时返回 `400`；Gin 默认会忽略 Request 结构体中未定义的 JSON 字段。

## 8. 运营端 API

### 8.1 创建商品

`POST /api/v1/admin/products`

请求：

```json
{
  "name": "Go 语言实战课程",
  "description": "面向有编程基础的学习者"
}
```

成功：

- 返回 `201 Created`。
- 商品状态为 `draft`。
- SKU 数组为 `[]`。

### 8.2 查询商品列表

`GET /api/v1/admin/products?page=1&page_size=20&status=draft&keyword=Go`

查询参数：

| 参数        | 必填 | 说明                           |
|-------------|------|--------------------------------|
| `page`      | 否   | 页码                           |
| `page_size` | 否   | 每页数量                       |
| `status`    | 否   | 精确过滤商品状态               |
| `keyword`   | 否   | 商品名称包含匹配，去除首尾空白 |

要求：

- 管理端可以看到全部状态的商品。
- 列表项包含 SKU 数量，但不返回完整 SKU 数组。

### 8.3 查询商品详情

`GET /api/v1/admin/products/:product_id`

要求：

- 返回商品完整字段和全部 SKU。
- SKU 按创建时间从旧到新排序。

### 8.4 修改商品信息

`PATCH /api/v1/admin/products/:product_id`

请求示例：

```json
{
  "name": "Go Web 实战课程",
  "description": "使用 Gin 构建后端服务"
}
```

要求：

- 至少提供一个可修改字段。
- `null` 不表示清空字段，传入 `null` 返回参数错误。
- 本接口不能修改商品状态。
- 成功返回更新后的完整商品。

### 8.5 修改商品状态

`PUT /api/v1/admin/products/:product_id/status`

请求：

```json
{
  "status": "on_sale"
}
```

要求：

- 按第 6 节执行状态迁移校验。
- 成功返回更新后的完整商品。

### 8.6 删除商品

`DELETE /api/v1/admin/products/:product_id`

要求：

- 遵循第 6.3 节删除规则。
- 成功返回 `204 No Content`。
- `204` 响应不能有响应体。

### 8.7 创建 SKU

`POST /api/v1/admin/products/:product_id/skus`

请求：

```json
{
  "code": "GO-COURSE-ONLINE",
  "specs": {
    "版本": "电子版"
  },
  "price_cent": 9900,
  "stock": 100
}
```

要求：

- 关联商品必须存在。
- SKU code 全局唯一。
- 状态默认是 `active`，请求不能指定状态。
- 成功返回 `201 Created` 和 SKU 数据。

### 8.8 修改 SKU

`PATCH /api/v1/admin/products/:product_id/skus/:sku_id`

允许修改：

- `specs`
- `price_cent`
- `stock`
- `status`

要求：

- 至少提供一个字段。
- SKU code 创建后不可修改。
- SKU 必须属于路径中的商品，否则按不存在处理。
- 修改状态时遵循第 6.2 节规则。
- 成功返回更新后的 SKU。

### 8.9 删除 SKU

`DELETE /api/v1/admin/products/:product_id/skus/:sku_id`

要求：

- SKU 必须属于路径中的商品。
- 遵循第 6.3 节删除规则。
- 成功返回 `204 No Content`。

## 9. 消费者端 API

### 9.1 查询在售商品列表

`GET /api/v1/products?page=1&page_size=20&keyword=Go`

要求：

- 只返回状态为 `on_sale` 的商品。
- 只统计并返回 `active` SKU。
- 列表项包含最低价格 `min_price_cent`。
- 没有 active SKU 的商品不会出现在列表中。
- 支持按商品名称进行包含匹配。

### 9.2 查询在售商品详情

`GET /api/v1/products/:product_id`

要求：

- 只有 `on_sale` 商品可以被查询。
- 只返回 `active` SKU。
- SKU 库存可以返回，但消费者不能通过任何接口修改。
- 草稿、下架和不存在的商品均返回 `404`，不能借此探测后台数据。

## 10. 健康检查

`GET /health/live`

成功响应：

```json
{
  "status": "ok"
}
```

要求：

- 返回 `200 OK`。
- `/health/ready` 检查 MySQL 是否可连接。
- Redis 尚未引入，因此不在健康检查范围内。
- 不返回版本、路径等不必要的内部信息。

## 11. 状态码

| HTTP 状态及响应 `code` | 场景                                               |
|------------------------|----------------------------------------------------|
| 400                    | JSON、路径、分页、查询参数或业务字段校验失败       |
| 404                    | 商品或 SKU 不存在，或者消费者不可见               |
| 409                    | 唯一键冲突、非法状态迁移或尝试删除在售资源         |
| 500                    | 未预期的服务内部错误                               |

同一响应中的 HTTP 状态码与 JSON `code` 必须保持一致。

## 12. 工程设计约束

### 12.1 目录建议

第一阶段建议形成以下目录，不需要创建后续阶段的空模块：

```text
.
├── config
│   └── config.go
├── controllers
│   └── product_controller.go
├── database
│   └── mysql.go
├── main.go
├── models
│   ├── product.go
│   └── errors.go
├── repositories
│   └── mysql_repository.go
├── routes
│   └── router.go
├── services
│   └── product_service.go
├── config.yaml
├── docs
├── go.mod
└── go.sum
```

测试文件放在被测试代码附近。允许根据实现调整文件粒度，但不能把所有逻辑继续堆在 `main.go`。项目采用传统按层 MVC，model、repository、service、controller 和 route 位于根级独立目录。

PRD-001 保留根目录 `main.go` 作为唯一程序入口。只有在后续阶段确实出现 API、worker、migration 等多个独立运行入口时，才评估迁移到 `cmd/` 目录。

### 12.2 职责边界

- controllers：解析路径、查询和 JSON，请求 services，并转换为 HTTP/JSON 响应。
- service：执行校验、状态迁移、消费者可见性和业务流程。
- repository：保存数据并保证原子读写，不依赖 Gin。
- model：表达领域对象，不包含 HTTP 请求上下文。
- routes：注册路由和通用中间件。
- config：读取和校验 YAML 配置。
- database：建立 GORM/MySQL 连接与连接池。
- main：组装依赖、启动和关闭服务。

本项目是 REST API，不渲染服务端 HTML 模板，因此不单独创建传统 `views` 目录；JSON 响应模型由 controllers 负责，领域 models 不承担 HTTP 流程。

### 12.3 依赖规则

- controllers 可以依赖 services 接口或具体服务。
- services 依赖 repositories 接口。
- MySQL repository 实现该接口。
- repositories 只依赖 models，不能反向依赖 services、controllers 或 Gin。
- models 不依赖 repositories、services、controllers 或 Gin。
- 不使用包级可变 map、计数器或 service 单例。

### 12.4 数据库与并发规则

- MySQL 使用 InnoDB、`utf8mb4`、UTC 时区和严格 SQL 模式。
- 商品和 SKU ID 由 MySQL 自增主键生成。
- SKU code 使用数据库唯一索引保证并发唯一性。
- 商品与所属 SKU 的级联软删除必须在同一事务中执行。
- Repository 的数据库调用必须携带 `context.Context`。
- 集成测试必须覆盖并发写入、事务、JSON 规格和软删除。

### 12.5 错误规则

- 使用稳定的领域错误值或错误类型表达可预期失败。
- 使用 `errors.Is`/`errors.As` 判断包装后的错误。
- controller 不能通过比较错误文本决定 HTTP 状态。
- 未预期错误记录服务端日志，对客户端统一返回 `500` 和通用错误消息。

### 12.6 服务启动与关闭

- 不能忽略 `http.Server.ListenAndServe` 返回的错误。
- 使用显式 `http.Server`，不直接依赖 `router.Run()` 完成最终启动。
- 响应 `SIGINT`/`SIGTERM` 并调用 `Shutdown` 优雅关闭。
- 监听地址通过环境变量配置，默认 `:8080`。

## 13. 测试要求

### 13.1 Service 单元测试

至少覆盖：

1. 创建商品后状态为 `draft`。
2. 名称过短、过长或仅包含空白时失败。
3. 创建合法 SKU 成功。
4. SKU code 重复时失败。
5. 没有 active SKU 的商品不能上架。
6. 商品可以上架、下架和重新上架。
7. 非法状态迁移失败。
8. 上架商品不能删除。
9. 上架商品不能删除 SKU。
10. 消费者只能查询上架商品和 active SKU。

### 13.2 Repository 单元测试

至少覆盖：

1. 创建后可以按 ID 查询。
2. 更新不存在的资源返回未找到错误。
3. 删除商品时在事务中软删除所属 SKU。
4. SKU 规格可以正确写入和读取 JSON 字段。
5. 并发创建相同 SKU code 时只有一个成功。
6. 商品筛选、分页和软删除查询正确。

### 13.3 HTTP 测试

使用 `httptest` 至少覆盖：

1. 创建商品返回 `201` 和正确响应结构。
2. 非法 JSON 或字段类型错误返回 `400`。
3. 列表空数据返回 `[]` 和正确分页信息。
4. 非法分页参数返回 `400`。
5. 删除成功返回无响应体的 `204`。
6. 消费者查询草稿或下架商品返回 `404`。
7. 业务错误可以稳定映射为约定 HTTP 状态和错误码。

### 14.2 递进实现原则

每个业务功能都按相同顺序接通：

1. 先确定 URL、请求参数、成功响应和失败响应。
2. 在 `Repository` 接口中只增加当前功能需要的方法。
3. 在 `MySQLRepository` 中使用 GORM 实现数据库操作。
4. 在 Service 中调用 Repository，并放置业务规则。
5. 在 Controller 中获取客户端参数、调用 Service、转换 HTTP 响应。
6. 在 Router 中注册路由。
7. 使用 `curl` 手动验证成功和失败场景。
8. 当前功能理解并跑通后，再进入下一个功能。

Controller、Service、Repository 的职责不能混合。Controller 负责 HTTP，Service 负责业务规则，Repository 负责数据库操作。

### 14.3 阶段一：创建商品（已完成）

接口：`POST /api/v1/admin/products`

实现内容：

1. Controller 使用 `c.ShouldBindJSON` 获取 JSON 请求参数。
2. Service 校验商品名称和描述，并设置默认状态 `draft`。
3. Repository 使用 `db.WithContext(ctx).Create(&product)` 写入 MySQL。
4. 使用统一的 `{code, data}` 或 `{code, message}` 格式响应客户端。

本阶段学习点：Gin JSON 参数绑定、结构体分层转换、GORM `Create`、MySQL 自增 ID、统一响应。

完成标准：合法商品返回 `201`，数据库产生记录；非法名称返回 `400`。

### 14.4 阶段二：查询单个商品（下一步）

接口：`GET /api/v1/admin/products/:product_id`

按以下顺序实现：

1. 明确路径参数 `product_id` 必须是大于 0 的整数。
2. 增加领域错误 `ErrProductNotFound`。
3. Repository 增加 `GetProduct(ctx, productID)`，使用 GORM `First` 按主键查询。
4. Repository 将 `gorm.ErrRecordNotFound` 转换为 `ErrProductNotFound`。
5. Service 增加 `GetProduct`，当前只负责调用 Repository，不提前加入 SKU 查询。
6. Controller 使用 `c.Param("product_id")` 获取路径参数，并用 `strconv.ParseUint` 转成 `uint64`。
7. Controller 将非法 ID 映射为 `400`，不存在商品映射为 `404`。
8. Router 注册 `GET /api/v1/admin/products/:product_id`。

本阶段学习点：Gin 路径参数、字符串转整数、GORM `First`、跨层传递和转换错误、HTTP `404`。

完成标准：存在的 ID 返回商品；非法 ID 返回 `400`；不存在的 ID 返回 `404`。

### 14.5 阶段三：查询商品列表

接口：`GET /api/v1/admin/products?page=1&page_size=20&status=draft&keyword=Go`

按以下顺序实现：

1. 定义 `ProductListQuery`，使用 `form` 标签描述 Query 参数。
2. Controller 使用 `c.ShouldBindQuery` 获取 Query 参数。
3. Service 校验并补充分页默认值：`page=1`、`page_size=20`，最大 `page_size=100`。
4. Repository 使用 GORM `Where`、`Order`、`Limit`、`Offset` 和 `Count` 查询。
5. 定义包含列表和分页信息的响应类型。
6. Router 注册 `GET /api/v1/admin/products`。

本阶段学习点：Gin Query 绑定、分页、条件查询、链式 GORM、切片 JSON 响应。

完成标准：无数据时返回空数组；分页和筛选有效；非法分页参数返回 `400`。

### 14.6 阶段四：修改商品信息

接口：`PATCH /api/v1/admin/products/:product_id`

按以下顺序实现：

1. 定义 `UpdateProductRequest`，使用指针区分“客户端没有传字段”和“客户端传了空字符串”。
2. Controller 同时获取路径参数和 JSON 请求体。
3. Service 校验至少传入一个字段，并复用商品名称、描述校验规则。
4. Repository 使用 GORM `Updates` 更新允许修改的字段。
5. 返回更新后的商品，不允许在这个接口中修改商品状态。

本阶段学习点：`PATCH` 语义、指针零值、部分更新、限制可更新字段。

完成标准：可以单独修改名称或描述；空请求返回 `400`；不存在商品返回 `404`。

### 14.7 阶段五：删除商品

接口：`DELETE /api/v1/admin/products/:product_id`

按以下顺序实现：

1. Controller 解析路径参数。
2. Service 查询商品状态并执行删除业务规则。
3. Repository 使用 GORM `Delete` 进行软删除。
4. 成功返回 `204 No Content`，不存在商品返回 `404`。

本阶段学习点：HTTP `DELETE`、GORM 软删除、删除规则和空响应体。

完成标准：删除后普通查询无法找到记录；数据库中的 `deleted_at` 有值。

## 15. 验收场景

### 场景 A：商品从草稿到上架

1. 创建商品，得到 `draft` 商品和空 SKU 列表。
2. 直接上架，返回 `409` 和对应错误消息。
3. 创建一个 active SKU。
4. 再次上架，成功变为 `on_sale`。
5. 消费者列表和详情都能看到该商品。

### 场景 B：消费者数据隔离

1. 创建草稿商品及 SKU。
2. 管理端可以查询商品详情。
3. 消费者端查询相同商品返回 `404`。
4. 上架后消费者可见。
5. 下架后消费者再次查询返回 `404`。

### 场景 C：SKU 约束

1. 为商品创建 SKU `BOOK_GO_001`。
2. 为另一个商品创建相同 code，返回 `409` 和对应错误消息。
3. 创建负价格、负库存或空规格 SKU，均返回 `400`。
4. SKU code 创建后不能通过修改接口改变。

### 场景 D：删除规则

1. 草稿商品可以删除，所属 SKU 同时消失。
2. 上架商品不能删除。
3. 下架商品可以删除。
4. 删除不存在资源返回 `404`。

### 场景 E：并发安全

1. 并发创建多个商品和 SKU，ID 不重复。
2. 并发创建相同 SKU code，只有一个成功。
3. 在并发查询、修改和删除时不发生 panic。
4. `go test -race ./...` 不报告数据竞争。
