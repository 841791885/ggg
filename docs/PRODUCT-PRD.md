# 单商户商城系统总 PRD

## 1. 文档信息

- 产品名称：GoMall（暂定）
- 文档类型：产品总 PRD
- 状态：待确认
- 目标：定义系统最终功能、业务价值与产品边界
- 实施方式：按阶段 PRD 渐进交付，每阶段在已有系统上演进

## 2. 产品定位

GoMall 是一个面向消费者和商城运营人员的单商户自营商城系统。消费者可以完成从浏览商品到下单、支付和查看订单的完整购物流程；运营人员可以管理商品、库存、订单和促销；管理员可以管理人员权限并查看系统运行状态。

项目最终应成为一个可部署、可测试、可观测、支持多实例运行的完整 Web 系统，而不是只演示增删改查的接口集合。

## 3. 建设意义

该系统用于解决三个层面的问题：

1. 产品层面：提供完整、连贯的线上购物和后台运营流程。
2. 工程层面：处理库存一致性、订单状态、支付幂等、缓存一致性和异步任务等真实问题。
3. 学习层面：通过持续演进掌握 Go、Gin、MySQL、Redis、Nginx、Docker、测试与可观测性。

## 4. 产品边界

### 4.1 本系统包含

- 单商户自营模式。
- 用户端商城 API 和运营管理 API。
- 商品、库存、购物车、订单、模拟支付、促销和售后基础流程。
- 可由独立前端项目接入的 RESTful API。
- MySQL 8 数据持久化和 Redis 缓存、限流、临时状态管理。
- 使用兼容 S3 的对象存储保存多实例共享的商品图片。
- Nginx 统一入口和 Docker Compose 本地或服务器部署。

### 4.2 本系统暂不包含

- 淘宝式多商户入驻、店铺结算与平台抽佣。
- 对接微信、支付宝等真实资金渠道。
- 对接真实快递公司和电子面单。
- 直播、内容社区、推荐算法和广告投放平台。
- 跨境税务、多币种和复杂财务核算。

这些边界用于控制项目规模，不代表系统设计可以忽略扩展性。

## 5. 用户角色

| 角色 | 说明 | 核心目标 |
| --- | --- | --- |
| 游客 | 未登录访问者 | 浏览和搜索商品，注册或登录 |
| 消费者 | 已注册普通用户 | 管理购物车、下单、支付和售后 |
| 运营人员 | 商城日常运营者 | 维护商品、库存、订单和促销 |
| 管理员 | 系统最高权限人员 | 管理运营账号、权限和系统配置 |

权限遵循最小授权原则。消费者不能访问运营数据，运营人员不能修改管理员权限。

## 6. 最终功能全景

### 6.1 用户注册与登录

**最终功能**

- 邮箱或用户名注册。
- 密码登录、退出登录和令牌刷新。
- 密码采用不可逆哈希保存。
- 查询和修改个人资料。
- 修改密码和重置密码的模拟流程。
- 连续登录失败时进行临时限制。

**功能意义**

用户系统用于识别操作主体，是购物车、地址、订单和售后的归属基础。安全的密码存储、令牌刷新和登录限制可以避免用户凭据泄露或被暴力尝试。

### 6.2 角色与权限

**最终功能**

- 区分消费者、运营人员和管理员。
- 根据角色限制管理接口。
- 管理员创建、停用运营账号。
- 关键管理操作记录操作者和时间。

**功能意义**

商城前台与后台的数据敏感程度不同。权限控制可以防止越权修改价格、库存和订单；操作记录用于追踪误操作和安全事件。

### 6.3 收货地址

**最终功能**

- 新增、修改、删除和查询收货地址。
- 设置一个默认地址。
- 下单时选择地址。
- 订单保存地址快照。

**功能意义**

地址是订单履约的必要信息。订单必须保存下单时的地址快照，否则用户后来修改地址会导致历史订单内容变化，破坏业务事实。

### 6.4 商品分类

**最终功能**

- 运营人员创建、编辑、排序和启停分类。
- 支持有限层级的父子分类。
- 消费者按分类筛选商品。
- 停用分类后不影响历史订单。

**功能意义**

分类帮助消费者发现商品，也为运营管理提供组织方式。启停而非直接物理删除，可以避免历史数据失去关联。

### 6.5 商品与 SKU

**最终功能**

- 创建和维护商品名称、介绍、主图、详情图及状态。
- 一个商品可以包含多个 SKU，例如不同颜色和容量。
- SKU 独立维护编码、规格、销售价格和库存。
- 商品支持草稿、上架和下架状态。
- 消费者查看商品列表与详情。

**功能意义**

SPU 表达消费者理解的商品，SKU 表达真正可购买和计库存的规格。将二者分开可以正确处理“同一商品不同规格、价格和库存”的现实场景。

### 6.6 商品搜索与筛选

**最终功能**

- 按关键词搜索商品名称。
- 按分类、价格范围和上架状态筛选。
- 支持价格、销量和上架时间排序。
- 所有列表接口支持分页。

**功能意义**

搜索和筛选降低消费者找到目标商品的成本。统一分页可以限制单次查询的数据量，避免商品增长后接口性能快速恶化。

### 6.7 库存管理

**最终功能**

- 每个 SKU 独立维护可售库存。
- 运营人员执行入库和库存调整。
- 保存库存变化流水及变更原因。
- 下单时预占库存，取消或超时后释放库存。
- 支付成功后确认扣减库存。
- 并发下单不能产生负库存或超卖。

**功能意义**

库存决定订单是否可以履约，是商城最关键的一致性数据之一。库存流水用于审计和排查差异；预占机制能在用户支付期间保留商品，同时避免永久占用。

### 6.8 购物车

**最终功能**

- 将指定 SKU 加入购物车。
- 修改购买数量、删除商品和批量选择。
- 合并同一 SKU 的重复添加。
- 展示商品当前价格、库存和有效状态。
- 下单前重新校验价格与库存。

**功能意义**

购物车保存的是购买意向，而不是最终交易承诺。商品价格、状态和库存可能随时变化，因此下单时必须以服务端实时数据重新计算，不能信任前端提交的价格。

### 6.9 订单创建

**最终功能**

- 从购物车选中项或单个 SKU 创建订单。
- 服务端计算商品金额、优惠金额、运费和应付金额。
- 生成全局唯一、不可预测的订单号。
- 保存商品名称、规格、价格和收货地址快照。
- 使用事务保证订单、订单项和库存预占的一致性。
- 相同请求重复提交不会创建多张订单。

**功能意义**

订单是一次交易的不可变事实记录。快照保证历史订单不受商品后续改动影响；事务与幂等机制防止网络重试造成重复订单或库存数据错乱。

### 6.10 订单状态与管理

**最终功能**

- 消费者查询订单列表和详情。
- 支持待支付、待发货、已发货、已完成和已取消等状态。
- 只允许合法的状态迁移。
- 消费者在允许条件下取消订单或确认收货。
- 运营人员查询订单并执行发货。
- 记录订单状态变化历史。

**功能意义**

订单不是一个可以任意修改的状态字段。明确状态机可以阻止“已取消订单再次支付”等非法操作，状态历史则为客服排查和业务审计提供依据。

### 6.11 模拟支付

**最终功能**

- 为待支付订单创建模拟支付单。
- 模拟支付成功、失败和支付回调。
- 支付回调支持签名校验的抽象接口。
- 重复回调不会重复扣款或重复修改订单。
- 保存支付流水号、金额、状态和回调记录。

**功能意义**

本项目不处理真实资金，但要实现真实支付系统最重要的边界：支付单独建模、验证订单金额、处理异步回调并保证幂等。未来接入真实渠道时只需替换支付适配器。

### 6.12 超时关单

**最终功能**

- 待支付订单超过规定时间后自动取消。
- 取消时释放预占库存。
- 已支付订单不能被超时任务取消。
- 任务重复执行不会产生副作用。

**功能意义**

未支付订单不能无限占用库存。超时关单用于恢复可售库存，同时要求任务具有幂等性，以应对重复调度和多实例竞争执行。

### 6.13 优惠券与促销

**最终功能**

- 运营人员创建满减优惠券并配置领取和使用时间。
- 用户领取、查看和使用优惠券。
- 限制每人领取数量和优惠券总量。
- 下单时由服务端验证适用范围并计算优惠。
- 取消订单后按规则返还优惠券。

**功能意义**

促销功能让项目覆盖更复杂的金额计算、时间规则和并发领取问题。优惠必须由服务端计算，避免客户端篡改金额。

### 6.14 发货与物流信息

**最终功能**

- 运营人员为已支付订单录入模拟承运商和物流单号。
- 消费者查看发货信息。
- 发货操作推动订单进入已发货状态。
- 重复发货请求应被拒绝或幂等处理。

**功能意义**

发货连接交易和履约流程。即使不接入真实物流平台，也需要验证订单状态并保存履约凭证。

### 6.15 退款与售后基础流程

**最终功能**

- 消费者对符合条件的订单项申请退款。
- 运营人员审核同意或拒绝。
- 通过模拟支付渠道执行退款。
- 保存申请原因、审核结果、退款金额和状态历史。
- 重复退款请求不会导致多次退款。

**功能意义**

售后让交易形成完整闭环，并进一步练习状态机、金额校验、权限边界和幂等处理。第一版只实现退款，不扩展换货与复杂仲裁。

### 6.16 评价

**最终功能**

- 已完成订单的购买者可以评价对应商品。
- 支持评分和文字内容。
- 同一订单项只能提交一次评价。
- 商品详情展示评价列表和平均评分。
- 运营人员可以隐藏违规评价，但保留审计记录。

**功能意义**

评价为消费者提供决策依据。绑定真实订单项可以降低虚假评价，隐藏而非删除有助于保留管理记录。

### 6.17 运营后台

**最终功能**

- 展示商品、库存、订单和用户的关键汇总数据。
- 管理分类、商品、SKU、库存和上下架状态。
- 处理发货和退款申请。
- 查看低库存商品和异常订单。
- 所有列表支持分页、筛选和必要的导出。

**功能意义**

消费者功能解决“买”的问题，运营后台解决“卖”和“履约”的问题。没有运营能力的商城无法长期维护商品和处理订单。

### 6.18 缓存

**最终功能**

- 使用 Redis 缓存商品详情和高频读取数据。
- 为缓存设置合理的过期时间。
- 商品更新后使相关缓存失效。
- 防止缓存穿透、击穿造成数据库压力突增。
- Redis 不可用时，核心购物流程可以受控降级。

**功能意义**

缓存降低数据库读取压力和接口延迟，但也会引入数据一致性问题。系统需要明确哪些数据可以缓存、如何失效，以及缓存故障时如何退回数据库。

### 6.19 限流与安全防护

**最终功能**

- 对登录、注册、下单和支付等敏感接口限流。
- 支持基于用户和 IP 的限制策略。
- 使用 Redis 与 Lua 保证多实例下限流的一致性。
- 校验输入长度、类型和业务范围。
- 配置跨域、安全响应头和敏感信息脱敏。

**功能意义**

限流可以降低暴力登录、恶意下单和突发流量对系统的影响。输入校验和信息脱敏用于缩小常见 Web 安全风险。

### 6.20 通知

**最终功能**

- 在支付成功、发货、取消和退款结果等节点生成站内通知。
- 通知异步发送，不阻塞订单主流程。
- 失败任务支持有限次数重试。
- 保存通知状态，避免重复发送。

**功能意义**

通知属于订单流程的副作用，不应该因通知服务失败而导致支付或发货失败。异步处理可以解耦核心交易与外围功能。

### 6.21 文件与商品图片

**最终功能**

- 运营人员上传商品图片。
- 校验文件类型和大小。
- 数据库仅保存文件标识或访问地址。
- 文件存储通过接口抽象，可在本地存储和对象存储之间替换。

**功能意义**

商品展示离不开图片。存储抽象可避免业务代码绑定单机磁盘，并为未来接入对象存储保留边界。

### 6.22 审计日志

**最终功能**

- 记录价格、库存、订单、退款和权限等关键管理操作。
- 包含操作者、时间、目标对象和必要的变更摘要。
- 审计记录不能由普通运营人员修改。
- 支持按操作类型、操作者和时间查询。

**功能意义**

价格和库存等误操作会产生直接业务影响。审计日志帮助回答“谁在什么时候修改了什么”，是问题追踪和权限治理的基础。

## 7. 核心业务规则

1. 所有商品金额使用最小货币单位的整数表示，例如人民币“分”，禁止使用浮点数计算金额。
2. 订单价格只能由服务端根据实时商品和促销数据计算。
3. 历史订单使用快照，不随商品、SKU 或地址变更。
4. 库存不能为负数，所有库存变化必须有流水。
5. 下单、支付回调、退款和超时任务必须具备幂等性。
6. 订单状态只能沿规定状态机迁移。
7. 删除核心业务数据优先采用停用或软删除，保留历史交易关联。
8. 核心交易写入必须使用数据库事务保证一致性。
9. Redis 是性能与协调组件，不能成为无法恢复的唯一业务数据源。
10. 所有时间由服务端生成并统一存储，API 使用 RFC 3339 格式输出。

## 8. 非功能需求

### 8.1 性能与扩展

- 所有列表接口必须分页并限制最大页大小。
- 高频读取数据允许使用 Redis 缓存。
- Go 服务保持无状态，可水平扩展为多个实例。
- Nginx 作为系统统一入口并提供负载均衡。
- 最终阶段通过压测给出商品查询和下单接口的性能基线。

### 8.2 可靠性

- 服务支持优雅停机，不中断正在处理的关键请求。
- MySQL 和 Redis 连接设置超时及连接池上限。
- 外部或异步操作失败时采用明确的重试与补偿策略。
- 健康检查区分进程存活和依赖就绪状态。

### 8.3 安全

- 密码和令牌不得写入日志。
- 配置和密钥通过环境变量或本地非提交配置注入。
- 管理接口必须进行身份认证和权限校验。
- 对上传文件、JSON 请求和查询参数设置大小限制。
- 数据库访问使用参数化查询。

### 8.4 可观测性

- 输出包含请求 ID 的结构化日志。
- 记录请求耗时、状态码和错误类型，不记录敏感数据。
- 暴露请求量、错误率、延迟和关键业务指标。
- 支持通过日志和指标定位一次失败订单的处理过程。

### 8.5 质量

- 核心业务规则具备单元测试。
- HTTP 接口具备集成测试。
- 数据库变更通过版本化迁移管理。
- 代码通过格式化、静态检查、单元测试和竞态检测。
- API 契约具有可维护的文档。

## 9. 最终部署形态

```text
Web 用户端 / Web 运营后台
              │
              ▼
            Nginx
       静态资源 / HTTPS / 限流
              │
        ┌─────┴─────┐
        ▼           ▼
   Go API 实例 1  Go API 实例 2
        │           │
        └─────┬─────┘
              │
       ┌──────┼──────────┐
       ▼      ▼          ▼
    MySQL   Redis      MinIO
  业务事实  缓存/限流   商品图片
    数据    /临时状态   对象存储
```

开发与演示环境最终通过 Docker Compose 启动全部依赖。前后端保持独立工程，通过稳定 API 契约协作；MinIO 仅作为开发和演示环境的 S3 兼容对象存储实现。

## 10. 最终验收结果

项目最终完成时，应能演示以下完整流程：

1. 管理员创建运营账号。
2. 运营人员创建分类、商品和 SKU，完成入库并上架。
3. 消费者注册登录，浏览和搜索商品。
4. 消费者将不同 SKU 加入购物车并领取优惠券。
5. 消费者提交订单，系统正确计算金额并预占库存。
6. 模拟支付成功后，订单进入待发货状态且重复回调不产生副作用。
7. 运营人员发货，消费者确认收货并评价商品。
8. 消费者发起退款，运营人员审核并完成模拟退款。
9. 未支付订单自动关闭并释放库存。
10. 并发购买有限库存时不超卖，恶意请求受到限流。
11. Redis 短暂不可用时系统按预定策略降级，恢复后数据仍以数据库为准。
12. Nginx 将请求分发至多个 Go 实例，任一实例不保存必须共享的业务状态。
13. 通过日志和指标可以定位订单、库存和支付处理结果。
14. 全套服务可以按照项目文档一键启动并通过自动化测试。
