# GoMall 分阶段实施路线图

## 1. 路线图目标

本路线图将《单商户商城系统总 PRD》拆分为连续、可验收的开发阶段。每个阶段只引入有限的新概念，同时保留和改造上一阶段的成果。

执行规则：

1. 每个阶段开始前发布独立的阶段 PRD。
2. 阶段 PRD 明确接口、数据模型、业务规则和验收用例。
3. 当前阶段验收通过后才进入下一阶段。
4. 不为后续需求预写尚未使用的代码。
5. 允许后续需求推动已有代码重构，但不推倒重写。
6. 每阶段至少完成格式化、静态检查、自动化测试和使用文档。

## 2. 总体技术路线

### 2.1 架构策略

项目采用**模块化单体**：部署时是一个 Go API 服务，代码内部按业务模块划分。它比单文件项目更容易维护，又避免初学阶段过早承担微服务的网络调用、数据一致性和运维成本。

最终建议目录形态：

```text
.
├── cmd/api                 # API 程序入口
├── internal
│   ├── auth                # 认证与权限
│   ├── catalog             # 分类、商品与 SKU
│   ├── cart                # 购物车
│   ├── inventory           # 库存与库存流水
│   ├── order               # 订单与状态机
│   ├── payment             # 模拟支付与退款
│   ├── promotion           # 优惠券
│   ├── notification        # 通知任务
│   └── platform            # 配置、数据库、缓存、日志等
├── migrations              # 数据库迁移
├── docs                    # PRD、API 和运行文档
├── deployments             # Nginx、Docker 等部署配置
└── tests                   # 跨模块集成测试
```

目录会随阶段逐步形成，第一阶段不需要一次创建全部空目录。

### 2.2 核心技术栈

| 领域 | 技术选择 | 使用理由 |
| --- | --- | --- |
| 语言 | Go | 强类型、并发模型清晰、适合网络服务 |
| HTTP 框架 | Gin | 路由和中间件成熟，学习成本适中 |
| 参数校验 | go-playground/validator | Gin 生态常用，支持结构体规则校验 |
| 主数据库 | MySQL 8（InnoDB） | 国内商城项目常见，事务和行锁足以支撑订单业务 |
| 数据库驱动 | `database/sql` + `go-sql-driver/mysql` | 使用标准接口并理解连接池、事务和驱动边界 |
| SQL 访问 | 手写参数化 SQL | 先理解 SQL、事务和数据边界，不由 ORM 隐藏细节 |
| 数据库迁移 | Goose | SQL 迁移简单直接，让表结构变化可重复、可追踪 |
| 缓存 | Redis + go-redis/v9 | 缓存、临时状态、限流和分布式协调 |
| 对象存储 | MinIO（S3 兼容） | 让多个 API 实例共享商品图片 |
| 身份认证 | JWT + HttpOnly Cookie 或 Bearer Token | 支持前后端分离并练习无状态认证 |
| 密码哈希 | bcrypt | 避免明文或可逆方式保存密码 |
| 日志 | 标准库 `log/slog` | Go 原生结构化日志，减少不必要依赖 |
| 指标 | Prometheus client | 采集请求和业务指标 |
| API 文档 | OpenAPI | 建立稳定、可供前端使用的接口契约 |
| 测试 | testing、httptest、testcontainers-go | 覆盖单元、HTTP 和真实依赖集成测试 |
| 网关 | Nginx | HTTPS、静态资源、反向代理和负载均衡 |
| 容器 | Docker、Docker Compose | 固化开发和部署依赖 |
| 前端 | 使用你熟悉的 React/Vue 技术栈 | 本项目重点是 Go，前端不重复制造学习负担 |

具体依赖版本在对应阶段引入时锁定，不提前安装所有依赖。

## 4. PRD-001：内存版商品与 SKU 管理

### 阶段目标

建立第一个结构清晰、并发安全、可自动化测试的 Gin 服务，跑通商品目录的最小业务闭环。

### 实现功能

- 创建、修改、查询、分页查询和删除商品。
- 创建和维护商品下的 SKU。
- 商品具有草稿、上架、下架状态。
- 只有上架商品可以出现在消费者查询接口。
- SKU 包含规格、价格和库存数量。
- 统一成功与错误响应格式。
- 健康检查接口。

### 使用技术

- Go module。
- Gin 路由、路由分组和中间件。
- `net/http` 状态码。
- `sync.RWMutex` 保护内存仓库。
- `crypto/rand` 或等效安全方式生成标识。
- 标准库 `testing`、`httptest`。

### 重点掌握

- struct、方法、接口和构造函数。
- handler、service、repository 的职责边界。
- 错误值的定义、包装和判断。
- 指针、slice/map 与并发读写。
- 依赖注入，而不是可变全局变量。
- HTTP 输入校验和 API 契约。

### 本阶段不做

- 不接数据库、Redis、登录、购物车和订单。
- 不使用 ORM。
- 不为了未来功能创建空模块。

### 阶段出口

- 商品和 SKU 的核心接口验收通过。
- `go test ./...`、`go test -race ./...`、`go vet ./...` 通过。
- 服务关闭后数据丢失属于本阶段预期行为。

### 为下一阶段铺路

Repository 接口让内存实现可以替换为 MySQL，实现业务层尽量不感知存储方式。

## 5. PRD-002：MySQL 持久化

### 阶段目标

用关系型数据库替换内存仓库，使商品数据可靠保存，并掌握数据库约束和事务基础。

### 实现功能

- 分类、商品、SKU 和库存持久化。
- 数据库唯一约束、外键、检查约束和索引。
- 商品列表分页、筛选和排序。
- 商品软删除或停用，保护历史关联。
- 上传商品图片并校验文件类型和大小。
- 通过存储接口保存图片，开发环境先使用本地文件存储。
- 启动时检查数据库连接。
- 提供开发数据初始化方式。

### 使用技术

- MySQL 8，所有业务表使用 InnoDB。
- 标准库 `database/sql` 与 `go-sql-driver/mysql`。
- 手写参数化 SQL。
- Goose 管理 SQL 迁移。
- `context.Context` 管理查询超时和取消。
- Gin multipart 文件上传和标准库文件操作。
- `testcontainers-go` 或独立测试数据库完成集成测试。

### 重点掌握

- 表、主键、外键、唯一约束和索引。
- SQL 注入的成因及参数化查询。
- 连接池配置与资源释放。
- InnoDB 行锁、事务隔离级别和死锁重试边界。
- `utf8mb4` 字符集、UTC 会话时区和严格 SQL 模式。
- 数据库错误向业务错误的转换。
- 单元测试与集成测试的区别。

### 本阶段不做

- 不引入 ORM、Redis和读写分离。
- 不接对象存储或 CDN，本地文件存储只是可替换实现。
- 不实现用户和订单。

### 阶段出口

- 服务重启后商品数据仍存在。
- 迁移可以在空数据库完整执行。
- 重复 SKU 编码等非法数据由应用和数据库共同阻止。
- 商品查询具备合理索引，并能解释基础执行计划。

### 为下一阶段铺路

数据库和迁移机制为用户、权限及后续交易表提供可靠基础。

## 6. PRD-003：用户认证与角色权限

### 阶段目标

建立用户身份和权限边界，区分消费者接口与运营管理接口。

### 实现功能

- 用户注册、登录、退出和刷新令牌。
- 查询和修改个人资料。
- 消费者、运营人员、管理员三种登录后角色。
- 管理接口增加认证和角色校验。
- 管理员创建、停用运营账号。
- 登录失败限制和安全审计基础记录。

### 使用技术

- bcrypt 密码哈希。
- JWT 访问令牌和刷新令牌。
- Gin 认证、授权中间件。
- HttpOnly Cookie 或 Bearer Token，在阶段 PRD 中结合前端部署方式确定。
- MySQL 保存用户、刷新令牌标识及权限数据。

### 重点掌握

- 身份认证与权限授权的区别。
- 密码不能加密保存，必须使用专用哈希算法。
- JWT 过期、刷新、吊销和密钥管理。
- `context` 在请求链路中传递当前用户。
- 防止水平越权和垂直越权。

### 本阶段不做

- 不接第三方登录和短信服务。
- 不实现复杂 RBAC 权限配置界面。

### 阶段出口

- 未登录请求无法访问受保护接口。
- 消费者不能调用商品管理接口。
- 停用账号的令牌不能继续获得有效访问权限。
- 日志和响应不泄露密码、哈希或完整令牌。

### 为下一阶段铺路

所有消费者数据都可以可靠关联到当前用户，为地址、购物车和订单归属提供基础。

## 7. PRD-004：收货地址与购物车

### 阶段目标

让消费者建立购买清单并准备下单，同时练习用户私有资源的权限校验。

### 实现功能

- 收货地址增删改查和默认地址。
- 购物车添加 SKU、修改数量、删除和选择商品。
- 同一用户同一 SKU 自动合并数量。
- 购物车展示商品当前价格、状态和库存提示。
- 商品下架后购物车保留记录，但标记为不可购买。
- 下单预览由服务端重新计算商品金额。

### 使用技术

- MySQL 保存地址和第一版购物车。
- SQL 事务处理默认地址切换。
- OpenAPI 开始维护用户端接口契约。
- 表驱动测试覆盖不同用户的数据隔离。

### 重点掌握

- 一对多和多对多关系建模。
- 资源所有权校验。
- 为什么购物车价格不是订单成交价格。
- 批量查询与 N+1 查询问题。

### 本阶段不做

- 暂不使用 Redis 存储购物车。
- 不真正生成订单和扣减库存。

### 阶段出口

- 用户只能读写自己的地址和购物车。
- 默认地址始终最多只有一个。
- 前端篡改价格不会影响服务端计算结果。
- 无效或下架 SKU 不能进入下单预览结果的可购买项。

### 为下一阶段铺路

下单预览形成订单计算的输入边界，下一阶段将其固化为订单和商品快照。

## 8. PRD-005：订单、库存与并发控制

### 阶段目标

实现商城最核心的交易写入，保证并发下单时订单与库存一致且不超卖。

### 实现功能

- 从购物车选中项或立即购买创建订单。
- 订单保存商品、SKU、价格和地址快照。
- 服务端计算商品总额和应付金额。
- 创建订单时预占库存。
- 消费者取消待支付订单并释放库存。
- 订单状态机和状态变更历史。
- 用户通过幂等键避免重复创建订单。
- 运营人员查询订单，消费者查询自己的订单。

### 使用技术

- MySQL InnoDB 事务。
- 条件更新或行级锁控制库存并发。
- 数据库唯一约束保存幂等键。
- Go 领域错误和订单状态机。
- 并发集成测试。

### 重点掌握

- ACID、隔离级别、锁和死锁。
- 乐观并发与悲观并发的取舍。
- 金额为什么使用最小货币单位整数。
- 状态机为何优于任意更新状态字段。
- 接口幂等与数据库唯一性的关系。

### 本阶段不做

- 不支付、不优惠、不发货。
- 不使用 Redis 分布式锁代替数据库事务。

### 阶段出口

- 订单、订单项和库存预占要么全部成功，要么全部失败。
- 高并发购买有限库存时不会产生负库存。
- 重复幂等请求只返回同一张订单。
- 非法订单状态迁移被拒绝。

### 为下一阶段铺路

正确性先由数据库保证，下一阶段 Redis 只用于提速和辅助协调，不成为订单事实来源。

## 9. PRD-006：Redis 缓存与购物车优化

### 阶段目标

引入 Redis 优化高频读取和临时数据，理解缓存带来的性能收益与一致性成本。

### 实现功能

- 缓存商品详情和热门列表。
- 商品修改后正确失效相关缓存。
- 防止不存在商品造成缓存穿透。
- 热点缓存失效时避免大量请求同时访问数据库。
- 将购物车迁移或镜像到 Redis，并定义持久化策略。
- Redis 故障时商品查询可回退数据库，关键交易保持可控。

### 使用技术

- Redis。
- `go-redis/v9`。
- Cache Aside 模式。
- TTL 随机抖动、空值缓存、singleflight 或互斥重建。
- Redis 集成测试。

### 重点掌握

- 缓存穿透、击穿、雪崩的区别。
- 缓存一致性与最终一致性。
- Redis 数据类型和过期策略。
- 为什么缓存不能是订单和库存的唯一数据源。

### 本阶段不做

- 不做复杂多级缓存。
- 不把库存最终正确性完全交给 Redis。

### 阶段出口

- 缓存命中时减少数据库查询。
- 商品更新后不会长期返回旧数据。
- Redis 临时不可用时按设计降级，而不是导致进程崩溃。
- 有缓存命中率和降级次数的基础观测数据。

### 为下一阶段铺路

Redis 为支付防重、限流和异步任务协调提供基础，但各业务仍保持清晰的数据归属。

## 10. PRD-007：模拟支付与幂等回调

### 阶段目标

完成订单支付闭环，重点练习外部回调、金额校验和重复请求处理。

### 实现功能

- 待支付订单创建支付单。
- 模拟支付成功、失败和取消。
- 模拟支付渠道异步回调。
- 验证支付单、订单、用户和金额一致性。
- 重复回调不重复修改订单或库存状态。
- 保存支付流水和原始回调摘要。
- 支付成功后订单进入待发货状态。

### 使用技术

- MySQL 事务和唯一约束。
- HMAC 模拟回调签名。
- 支付 Provider 接口隔离渠道实现。
- 幂等消费模式。

### 重点掌握

- 支付单与订单为何是不同领域对象。
- 同步返回不等于最终支付结果。
- 至少一次投递下如何保证业务效果只有一次。
- 外部系统超时和未知状态的处理。

### 本阶段不做

- 不连接真实支付渠道。
- 不保存银行卡或其他敏感支付信息。

### 阶段出口

- 正确支付能推动订单状态。
- 金额不匹配或签名错误的回调被拒绝。
- 同一回调执行多次只有一次业务效果。
- 支付成功与订单更新在异常情况下不会产生明显不一致。

### 为下一阶段铺路

支付和订单事件将驱动通知与超时处理，下一阶段把这些副作用移出同步请求。

## 11. PRD-008：异步任务、超时关单与通知

### 阶段目标

将不应阻塞主请求的工作异步化，并实现可重试、可恢复、可幂等的后台任务。

### 实现功能

- 未支付订单超时自动关闭并释放库存。
- 支付成功、订单取消和发货产生站内通知。
- 任务保存状态、执行次数和最后错误。
- 失败任务有限重试并采用退避策略。
- 多实例不能重复产生业务副作用。
- 服务优雅停机，停止接收任务并等待处理中任务退出。

### 使用技术

- goroutine、channel、`context`、`sync.WaitGroup`。
- MySQL Outbox/任务表作为可靠事实来源。
- Redis 可用于任务唤醒或分布式互斥。
- 定时扫描作为第一版可靠实现。

### 重点掌握

- goroutine 生命周期与泄漏。
- channel 关闭和背压。
- 内存队列为什么无法保证进程重启后的任务可靠性。
- 重试、幂等、死信与补偿。
- Outbox 如何解决事务数据和事件发布的一致性。

### 本阶段不做

- 暂不引入 Kafka/RabbitMQ 等独立消息中间件。
- 不为了“异步”而拆分微服务。

### 阶段出口

- 服务重启后未完成任务仍能继续处理。
- 同一超时任务重复执行不会重复释放库存。
- 通知失败不影响支付和订单主流程。
- 竞态检测和 goroutine 退出测试通过。

### 为下一阶段铺路

可靠任务机制可复用于优惠券返还、退款和运营通知。

## 12. PRD-009：优惠券、发货、退款与评价

### 阶段目标

补齐交易后半程和基础营销，使系统具备完整商业流程。

### 实现功能

- 满减优惠券创建、领取、使用和过期。
- 下单时校验优惠条件并保存优惠明细。
- 运营人员为已支付订单发货。
- 消费者确认收货。
- 消费者申请退款，运营人员审核。
- 模拟渠道退款，重复请求保持幂等。
- 取消或退款时按规则处理优惠券和库存。
- 已完成订单项可以评价一次。

### 使用技术

- MySQL 事务、唯一约束和状态机。
- 规则计算服务。
- 异步任务复用。
- 表驱动测试覆盖金额和状态组合。

### 重点掌握

- 优惠计算顺序和金额不变量。
- 多个关联状态机如何协调。
- 历史快照与可审计流水。
- 售后流程中的权限和金额边界。

### 本阶段不做

- 不实现换货、真实物流轨迹和复杂促销叠加。
- 不实现多币种和税费系统。

### 阶段出口

- 优惠金额不会使应付金额小于零。
- 优惠券不能超领、重复使用或越权使用。
- 发货、收货、退款均只能从合法状态进入。
- 重复退款请求不会产生多次退款效果。

### 为下一阶段铺路

完整业务流程暴露出需要保护的高价值接口，下一阶段集中加入安全和流量治理。

## 13. PRD-010：限流、安全与审计

### 阶段目标

保护登录、下单、支付和管理接口，并让关键运营操作可追踪。

### 实现功能

- 按 IP 和用户限制登录、注册、下单、支付等接口频率。
- 对热点商品和库存接口设置合理保护。
- 管理员管理运营账号权限。
- 记录价格、库存、订单、退款和权限变更的审计日志。
- 统一请求体大小限制、输入校验和敏感字段脱敏。
- 配置 CORS 和常见安全响应头。

### 使用技术

- Redis Lua 实现多实例原子限流。
- 令牌桶或滑动窗口算法。
- Gin 安全中间件。
- 数据库审计表。
- Go fuzz test 测试关键解析和校验逻辑。

### 重点掌握

- 固定窗口、滑动窗口、漏桶和令牌桶的差异。
- 应用层限流与 Nginx 限流的边界。
- 认证、授权、输入校验和审计的组合关系。
- 可信代理和客户端 IP 获取规则。

### 本阶段不做

- 不自行实现密码学算法。
- 不把限流当作唯一的安全防线。

### 阶段出口

- 超限请求返回稳定的 `429` 响应和重试提示。
- 多个 Go 实例共享一致的限流状态。
- 日志和审计数据不包含密码、令牌等敏感信息。
- 可以查询某次价格或库存变更的操作者和时间。

### 为下一阶段铺路

应用已经具备多实例共享状态和安全边界，可以交给统一网关部署。

## 14. PRD-011：Nginx、多实例与 Docker Compose

### 阶段目标

把开发环境固化为可重复部署的完整系统，并验证 Go 服务无状态化。

### 实现功能

- 为 Go 服务构建多阶段 Docker 镜像。
- Docker Compose 启动 Nginx、多个 Go 实例、MySQL、Redis 和 MinIO。
- Nginx 提供反向代理、静态资源、请求大小限制和负载均衡。
- 商品图片从本地存储切换到 MinIO，多个 API 实例共享同一对象存储。
- 本地自签名或测试证书演示 HTTPS。
- 区分存活检查和就绪检查。
- 配置数据库迁移的安全执行方式。
- 服务接收终止信号后优雅停机。

### 使用技术

- Docker、Docker Compose。
- Nginx upstream、proxy、TLS 配置。
- Go 静态编译、多阶段镜像和非 root 用户运行。
- 环境变量和配置校验。

### 重点掌握

- 反向代理和负载均衡的请求链路。
- `X-Forwarded-For` 等代理头的信任边界。
- 容器网络、持久卷和健康检查。
- 为什么会话和任务不能依赖单个进程内存。

### 本阶段不做

- 不上 Kubernetes。
- 不购买域名或接入生产证书。
- 不将数据库打包进 Go 应用容器。

### 阶段出口

- 一条 Compose 命令可启动全套环境。
- Nginx 能将请求分配到至少两个 Go 实例。
- 停止其中一个实例后，系统仍能通过健康实例服务。
- 数据库和 Redis 数据使用明确的持久化卷。
- 配置文件不包含提交到仓库的真实密钥。

### 为下一阶段铺路

稳定的部署形态使压测、指标采集和故障演练具有可重复环境。

## 15. PRD-012：可观测性、压测与最终验收

### 阶段目标

让系统性能可以量化、故障可以定位，并完成总 PRD 的最终验收。

### 实现功能

- 全链路请求 ID 和结构化日志。
- HTTP 请求量、错误率和延迟指标。
- 数据库连接池、Redis、任务积压等资源指标。
- 下单成功、库存不足、支付回调和退款等业务指标。
- Prometheus 抓取指标，可选 Grafana 展示。
- 商品查询、登录和下单场景压测。
- 运营看板展示商品、订单、库存、用户和任务的关键汇总数据。
- MySQL、Redis、MinIO 和单个 Go 实例故障演练。
- 完整开发、测试、迁移和部署文档。

### 使用技术

- 标准库 `log/slog`。
- Prometheus Go client。
- Grafana，可作为指标展示层。
- k6、Vegeta 或同类压测工具，阶段开始时选择一种。
- Go benchmark、pprof 和数据库执行计划。

### 重点掌握

- RED 指标：请求速率、错误率和耗时。
- 日志、指标和性能剖析的不同用途。
- P50、P95、P99 延迟含义。
- 用数据定位瓶颈，而不是凭感觉优化。
- 容量、超时和降级之间的关系。

### 本阶段不做

- 不为了数字好看隐藏错误或放宽正确性约束。
- 没有证据时不进行复杂架构重写。

### 阶段出口

- 可以通过请求 ID 追踪一次失败请求。
- 仪表盘能展示核心技术和业务指标。
- 压测报告说明环境、数据规模、并发模型、结果和瓶颈。
- 依赖故障时系统行为符合此前定义的降级策略。
- 总 PRD 的完整消费者与运营流程验收通过。

## 16. 每阶段统一质量门槛

每个阶段在功能验收之外，还必须满足：

```bash
go fmt ./...
go vet ./...
go test ./...
go test -race ./...
```

涉及数据库或 Redis 的阶段，还需要：

- 在隔离测试环境执行集成测试。
- 验证迁移可从空环境执行。
- 验证连接、事务和 goroutine 正确释放。
- 记录新增配置项及默认值。

提交阶段验收时，应提供：

1. 已完成需求列表。
2. 尚未完成或主动延期的内容。
3. 自动化测试结果。
4. 手工验收步骤。
5. 关键设计决策和已知限制。

## 17. 学习节奏建议

每阶段遵循以下循环：

1. 阅读阶段 PRD，只确认需求，不提前看完整实现。
2. 先设计数据结构、接口和错误，再编写 handler。
3. 用测试固定核心业务规则。
4. 完成功能并执行质量检查。
5. 发起验收和代码审查。
6. 根据审查意见修改，形成阶段提交。
7. 发布下一阶段 PRD，并评估旧设计是否需要重构。

遇到问题时可以指定帮助级别：

- `提示`：只指出思考方向。
- `诊断`：定位原因，不直接修改代码。
- `讲解`：解释相关 Go 或后端知识。
- `实现`：授权直接修改并补充测试。
