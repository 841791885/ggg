## A1. 下单事务与库存预占（防超卖）⭐ 最核心
- **PRD 依据**：PRD-005 第 6 节 | **难度**：★★★ | **状态**：✅ 已完成（2026-09-12，含取消释放、库存流水表 007、死锁重试；实测并发抢购无超卖、失败零残留流水）
- **现状**：`services/order_service.go` Create 只写订单不碰库存；SKU 表有 `stock >= 0` CHECK 约束但没有扣减逻辑
- **要做**：
  1. 创建订单时在同一事务内对每个 SKU 执行条件原子更新：`UPDATE skus SET stock = stock - ? WHERE id = ? AND stock >= ?`，RowsAffected=0 即库存不足回滚整单
  2. 多 SKU 按 id 升序加锁防死锁；捕获死锁错误做有限重试
  3. 取消订单时同事务释放预占；新增库存流水表记录每次变动
- **验收**：两个终端并发抢购限量库存，不产生负库存、不超卖；`go test -race` 通过
- **学到**：ACID、行锁、乐观 vs 悲观并发、为什么禁止"先查后改"

## A2. 模拟支付回调（HMAC + 幂等消费）⭐ 打通闭环的关键
- **PRD 依据**：PRD-007 | **难度**：★★★ | **状态**：✅ 已完成（2026-09-12，HMAC 验签 + 交叉校验+event_no 双保险幂等；同事件并发 x5 全 200 仅一次业务效果、错签名 400、乱序回调 409 进人工通道；UI 已改真实回调 + 轮询）
- **现状**：支付单停在 pending；UI 提示语里写明了这一缺口（admin-ui/app.js createPayment）
- **要做**：
  1. `POST /api/v1/payment-callbacks/mock`：验 HMAC 签名→校验金额/单号一致→落 payment_callback_logs
  2. 用 payments.event_no 唯一键做幂等：同一事件重复回调只有一次业务效果
  3. 支付成功、订单 pending_payment→paid、状态日志在同一事务
  4. 处理乱序：已取消订单收到成功回调走异常路径，不静默改状态
  5. 前端 createPayment 改为轮询真实支付状态
- **验收**：同一回调 curl 三次，订单只变一次；错签名被拒
- **学到**：至少一次投递下的幂等消费、外部系统未知状态处理

## A3. Worker：超时关单 + 事件通知
- **PRD 依据**：PRD-008 | **难度**：★★★★ | **状态**：✅ 已完成（2026-09-12，goroutine+select+WaitGroup 优雅停机；Outbox 随下单/支付回调原子落任务；实测超时自动关单释放库存、支付成功作废关单任务并投递站内信；遗留 running 启动自愈。多实例互斥依赖 ClaimDueTask 条件更新，未经双进程实测）
- **现状**：orders.expires_at 已在写入（下单后 30 分钟），background_tasks 表和运营重试 API 已就绪，但没有任何东西消费任务
- **要做**：
  1. main.go 启动后台 goroutine 定时扫描到期未付订单，关单 + 释放库存（复用 A1）同事务
  2. 支付成功/发货/退款事件写入 Outbox 任务表，worker 消费生成 notifications
  3. 失败退避重试（attempts/max_attempts/next_run_at 字段都建好了）
  4. SIGTERM 优雅停机：停止取任务、等待处理中任务退出
- **验收**：重启服务后未完成任务继续执行；重复执行关单只生效一次；goroutine 无泄漏
- **学到**：goroutine 生命周期、channel 背压、Outbox 模式

## A4. 优惠券并发防超发
- **PRD 依据**：PRD-009 | **难度**：★★☆ | **状态**：未开始
- **现状**：Claim 只校验 remaining > 0（读后判），并发下会超发
- **要做**：领取事务内 `UPDATE coupon_templates SET remaining = remaining - 1 WHERE id = ? AND remaining > 0`；per_user_limit>1 时重新设计 user_coupons 唯一键（当前每人每模板一张）
- **验收**：并发领 100 张限量券，发出数恰好 100
- **学到**：条件更新 vs 悲观锁的取舍

## A5. 预览批量化消除 N+1
- **PRD 依据**：PRD-004 第 5 节 | **难度**：★★☆ | **状态**：未开始
- **现状**：`buildPreviewRow` 每条明细单独查 SKU 和商品
- **要做**：收集 sku_id 一次 `IN` 查 SKU、再一次 `IN` 查商品，内存组装；repository 加 `GetSKUsByIDs`/`GetProductsByIDs`
- **验收**：购物车 50 条明细时 SQL 日志固定 3~4 条而非 100+ 条
- **学到**：N+1 识别与批量查询设计

## A6. 默认地址切换的数据库层兜底验证

## A8. 优惠计算接入下单
- **PRD 依据**：PRD-009 | **难度**：★★★ | **状态**：未开始
- **现状**：user_coupons.order_id、orders.discount_cent 字段已预留，计算逻辑为空
- **要做**：预览接受可选 user_coupon_id 试算减免；下单事务内再次验证门槛并原子占用券（unused→used）；多订单项按比例分摊优惠且尾差归最后一项；应付不为负
- **验收**：各种金额组合下 `total_cent = Σ小计 - discount_cent` 恒等
- **学到**：金额不变量与分摊算法
